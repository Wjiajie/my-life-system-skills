# 观察—修改—测试—验证

用可复查的反馈推进工作：观察现状，提出假设，最小修改，通过代码侧测试，再在真实环境验收。失败结果进入下一轮，完成结论与实际证据对应。

## 先确定范围

- 沿用用户指定的仓库、分支、平台、输入及已有授权，保留无关改动和暂存状态。执行项目已有的编译规则与强制 harness，不用本技能替代它们。
- 只读定位仅观察、复现和报告；用户只要文字或禁止修改仓库时，在回复中给出方案与记录。仅在明确要求时修改 AGENTS.md、安装工具或调整环境配置。
- 构建、电脑操控、设备操作及外部写入按当次任务授权执行；已有明确授权不重复询问。调用本技能本身不扩大权限或任务范围。
- 记录使用用户指定位置；没有位置约定时先在会话中记录。长任务确需持久化时选择任务已授权的产物目录，不自动向源码仓库添加规范或报告。

## 1. 观察：取得基线和验收标准

核对当前代码、应用入口、输入与环境。缺陷任务复现实际症状；功能任务明确要完成的用户路径。必要时先跑相关已有检查，区分既有失败与新增失败。

定义可观察的通过条件，如指定操作产生的画面/输出、错误消失或固定条件下的性能目标。性能问题先采集有实际工作负载的基线。未可靠复现时记录已尝试的范围，补日志、采样或对照实验。

进入修改前应能说明：当前实际发生了什么、与预期差在哪里，以及下一轮用什么证据判断成败。

## 2. 假设：选择可证伪的最小实验

每轮写清：“观察到 X，因此怀疑 Y；如果成立，改动 Z 应带来结果 W。”区分事实与推断，跨模块问题沿实际数据流检查边界。

缺少证据时先添加必要的临时诊断并复现。一次实验验证一个假设；多个文件共同构成同一修复时，说明它们的关系。

## 3. 修改与代码侧测试：让缺陷留下约束

这里的“测试”包括静态检查、单测和回归；单测会执行代码，不等同于静态分析。

- 可自动复现的逻辑缺陷优先红绿测试：先运行并确认测试因目标缺陷失败，再做最小修复并运行相关回归。读取输出和退出状态，保留失败原因及通过结果。
- 断言来自需求和故障证据。发现契约有误时说明并修正；保留有效断言对缺陷的约束，不以删除、跳过或降低断言换取通过。
- 设备、时序或视觉问题无法合理自动化时，说明边界，用可重复的运行实验取证。文档、注释和纯格式变更只做对应检查，不为了流程新增无价值测试。

代码侧检查通过后，继续完成任务要求的实际运行验证；mock 结果只覆盖其模拟的契约。

## 4. 实际验证：重走原场景

按授权构建必要范围，读取最终结果；确认运行入口和本次产物对应。存在多份动态库、缓存或源码副本时，核对实际加载身份。

通过现有电脑操控、浏览器、设备或接口工具重走原始路径。例如：IDE Run → 打开指定项目/草稿 → 播放或交互 → 观察最终画面 → 检查同期日志和指标。使用任务中实际可用的工具；不预设某款 IDE、设备或插件。

对照验收条件并检查受影响场景。性能、采样或多份运行产物问题，先读 [运行证据与测量](references/runtime-evidence.md)。

构建成功证明能生成产物；功能、画面和性能结论分别需要实际输出或测量。工具、权限或环境阻塞时，记录失败步骤与输出，继续其余已授权且独立可行的工作，并保留“运行未验证”状态。

## 5. 反馈、记录与完成

失败后保留新证据，回到观察并更新假设。撤回本轮无效改动时只处理本任务引入的内容。多轮没有新增证据或范围收敛时，重新采样、缩小复现、对照正常路径或核对运行产物，再决定修改；确需用户决策时给出具体分歧与证据。

每轮记录以下内容，原始输出通过位置引用；用户要求纯文字时直接写在回复中：

```text
第 N 轮：目标与假设
环境/基线：代码与产物身份、输入、配置、操作状态
修改：文件与概要、预期影响
代码侧测试：命令、退出状态/通过数、红绿结果或未执行原因
实际验证：构建/运行步骤、实际画面或行为、同期日志
实测与证据：指标、测量窗口、原始输出位置或工具结果
结论：假设是否成立、保留/撤回的改动、下一步或未验证项
```

移除临时诊断后，对最终交付版本重跑受影响的测试与运行验证。仅更新记录文字不重复无关构建和 UI 操作。

报告对应范围完成前，核对：验收条件已有当前版本证据，必要回归及适用的项目 harness 已完成，工作区只包含预期变更。存在缺口时分别报告“代码侧测试通过 / 构建未验证 / 运行未验证”等真实状态，并指出缺失证据。

用户需要了解方法来源时，读 [参考实践](references/sources.md)；不把网页中的安装、编排或提交步骤当作本任务的授权。
