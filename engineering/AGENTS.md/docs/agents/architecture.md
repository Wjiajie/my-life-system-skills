# 架构手册

适用：设计新模块、新增功能、跨模块改动、架构评审或重构。项目自己的模块地图在根目录 `ARCHITECTURE.md`；本手册给出它没有另行规定时的默认做法。

## 1. 默认形态

**按功能划分的模块化单体。** 顶层目录按业务能力（领域）切分，而不是按技术类型（controllers、services、utils）切分；一个功能的代码尽量待在同一个模块里。

每个模块内部分三圈，依赖只能由外向内：

```
入口层（界面、路由、CLI、定时任务）
  └─> 模块公开接口（用例编排）
        └─> 领域核心（纯逻辑：输入普通数据，返回普通数据）
适配器（数据库、文件、网络、第三方服务）——实现领域需要的接口，由入口层组装后传入
```

- 领域核心可以脱离框架、数据库和网络单独测试。
- 模块之间只调用对方的公开接口，不读对方的内部文件、表或缓存。
- 只有当一个依赖确实存在两种以上实现（例如真实服务和测试替身），才为它设接口；只有一种实现时直接调用。

CQRS、事件溯源、微服务、多层仓储这类重型模式，只在 `ARCHITECTURE.md` 记录了具体需求时才引入。

## 2. 设计原则

这些是约束而不是清单。两条冲突时，选这个仓库未来成本最低的一方，并在提交说明里写明理由。

- **关注点分离**：编辑一个文件前，说出它负责的那一件事。
- **单一职责**：描述一个函数或模块时用到「和」，就拆开。命名表达意图，注释解释原因。
- **深模块**：用小接口藏住大量行为。判断方法：想象删掉这个模块，复杂度会消失（说明它只是转手），还是会散落到所有调用方（说明它值得存在）。
- **高内聚、低耦合**：改一条业务规则，只需要改一个模块。
- **单一来源**：每条规则、阈值、格式、数据结构只有一个归属位置。写新逻辑前先搜索；只是碰巧长得像的代码不要合并抽象。
- **简单优先**：函数优于类，组合优于继承；只为已经发生过两次的变化留扩展点；选成熟、常见的技术。
- **快速失败**：在边界处校验输入，错误要么处理、要么上抛，不静默吞掉。
- **为删除而优化**：功能能被整块移除，而不必在全仓库里找残留。

## 3. 新增功能流程

1. 读 `ARCHITECTURE.md`，确定功能归属的模块。找不到归属时，先提出新增模块的方案，经用户确认再继续。
2. 搜索要用到的已有逻辑（计算式、格式串、阈值、数据结构），列出全部副本。
3. 结构放不下新功能，或已有逻辑分散在多处时，先做重构：行为不变、测试保持通过、单独提交。合并副本时保留每个调用方原有的结果（边界判断、取整、截断）。
4. 在归属模块里实现，通过模块公开接口写测试。
5. 新增模块或改变依赖关系时，同步更新 `ARCHITECTURE.md`。
6. 运行架构检查和测试。

## 4. 架构评审

用数字，不用观点。对选定的系统统计：

- 某一领域的逻辑分布在多少个文件里；
- 同一条规则或公式有几份副本，其中几份结果不一致；
- 入口层或展示层里出现了多少处业务计算；
- 循环依赖，以及为绕开循环而写在函数内部的导入；
- 超大文件和超长函数（参考线：文件超过约 400 行、函数超过约 50 行时需要说明理由）；
- 架构检查的通过数与总数。

每个问题附「文件:行号」和违反的原则。然后给出分步重构计划：每步行为不变、单独提交、不夹带新功能。执行完后，用同一套数字复评，未达标的项回到计划里继续处理。最后补一条检查，防止同类问题回潮。

## 5. 强制执行

- **硬性规则（必须）**：写成工具检查，放进 CI 或提交前钩子。依赖方向和模块边界按技术栈选工具，例如 TypeScript/JavaScript 用 dependency-cruiser 或 eslint-plugin-boundaries，Python 用 import-linter，Java 用 ArchUnit，.NET 用 NetArchTest。
- **建议规则（应当）**：在评审中逐条对照，需要上下文判断的交给代理评审，并引用具体文件、行号和规则。
- 新规则先作为建议观察一段时间，确认合理后再升级为硬性检查。

## 6. `ARCHITECTURE.md` 模板

写第一批代码时，在根目录按以下结构创建，并随模块变化保持更新：

```markdown
# ARCHITECTURE.md

## 模块地图
| 模块 | 负责的领域 | 公开接口 | 允许依赖 | 规则文档 |
|------|------------|----------|----------|----------|

## 依赖方向
（一张图或一段说明：谁可以依赖谁）

## 新功能放在哪里
（常见功能类型 → 归属模块）

## 已知例外
| 位置 | 违反的原则 | 原因 | 计划 |
|------|------------|------|------|
```
