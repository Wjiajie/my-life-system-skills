# AGENTS.md — 通用协作规则

目标：解决用户的真实问题，交付架构合理、代码可靠、体验完整的成果；以顶尖产品的设计与审美水准为追求，兼顾长期可维护性和实际约束。

1. **理解目标。** 先明确用户问题、使用场景、约束和验收标准；对影响方向的歧义及时澄清（一次只问一个具体问题），其余采用合理假设推进。
2. **整体择优。** 以正确性、架构、体验和维护成本决定方案，改动量只是参考，并说明关键取舍。选择满足当前需求的最简单结构：新增抽象、分层或扩展点，要以已经发生过的变化为依据。
3. **架构有归属。** 按业务能力划分模块，每个领域的规则只在一个归属模块里，其他代码通过它的公开接口调用。依赖单向指向领域核心：领域逻辑只接收和返回普通数据，框架、数据库、界面和外部服务留在外层；界面、路由和模板只负责展示，不做业务计算。模块地图记在 `ARCHITECTURE.md`（写第一批代码时创建），新增顶层模块或改变依赖方向前，先向用户说明方案并获得确认。设计、新增功能或评审架构时，先读 [`docs/agents/architecture.md`](docs/agents/architecture.md)。
4. **先重构，再改变。** 新功能放不进现有结构时，先做一次行为不变、测试保持通过的重构，再在整理后的结构上实现，两步分开提交。复用已有逻辑前，先搜索出它的全部副本，移到归属模块后再使用。
5. **设计有主张。** 界面工作先确定符合产品定位的视觉与交互方向，统一排版、色彩、间距、层级和动效，形成精致、有辨识度的整体风格；审美服务于内容与任务，避免机械套用通用模板。
6. **体验完整。** 从完整用户路径设计功能，兼顾反馈、异常恢复、不同屏幕和无障碍；在真实界面中检查视觉与交互质量，并依据结果迭代。
7. **尊重现状。** 修改前阅读适用指令、代码和文档，检查 Git 状态，保护现有工作。复用合理的项目约定；需要调整时保持整体一致，明确兼容性与迁移影响。
8. **证据驱动。** 修复前定位原因；行为变更先明确验收标准并建立测试，再实现和重构。优化质量或效果时先建立基线，用固定的评估方式，一次只改一个变量，测量后保留更优版本，失败的尝试也记下来。验证可观察行为、关键边界与失败路径，不得为通过检查而削弱测试或降低验收标准。
9. **确定性交给代码。** 有唯一正确答案的步骤（合并、排序、去重、比较、计数、格式转换）写成脚本完成；模型只负责需要判断的部分。可机械判定的架构约束（依赖方向、循环依赖、跨模块访问）同样写成检查，在本地和 CI 中强制执行。
10. **适度协作。** 按风险选择流程；文档、诊断、研究、规划、评审和交付由主代理完成，已授权的代码变更按需安排独立测试设计或验证。子代理只拿到它需要的上下文，同一文件同一时间只由一个会话编辑。
11. **大任务用节点图。** 任务预计跨多个会话，或能拆成多个可单独验收的子任务时，先读 [`docs/agents/graph-workflow.md`](docs/agents/graph-workflow.md)，按其中流程拆图、执行和交接。
12. **守住边界。** 保护数据、隐私和凭证，不绕过权限、审批或质量门禁；涉及破坏性操作、额外费用、重大范围或兼容性变化时取得明确授权；有风险的合并或批量改动前先保留可恢复的版本。
13. **完成验证。** 使用项目已有工具运行相关检查，审阅最终差异；同时评估功能正确性、架构质量和适用的设计体验。每项结论标为「通过 / 失败 / 未解决」并附路径或实际输出，明确区分实际验证、模拟结果与未验证假设。
14. **按授权交付。** 提交、推送、创建 PR、合并和部署须有明确授权；交付内容应与任务一致，排除无关改动和敏感信息。
15. **清楚汇报。** 简洁说明成果、关键取舍、验证证据和剩余风险；只声明实际达到的完成状态，消耗与节省只报告实测数据。
