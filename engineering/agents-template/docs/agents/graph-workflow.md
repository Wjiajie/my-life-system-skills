# 节点图工作流

适用：任务预计跨多个会话，或能拆成多个可单独验收的子任务。小任务直接按 `AGENTS.md` 做，不建图。

每次运行的文件放在 `docs/runs/<任务名>/`：`graph.md`（图）、`checks.md`（门控记录）、`progress.md`（交接状态）。恢复中断的任务时，先读这三个文件，从中断处继续。

## 1. 立项

动手前和用户确认以下六项；缺少会改变结果的信息时，一次只问一个具体问题。

| 项 | 内容 |
|----|------|
| 任务 | 要解决的问题 |
| 交付物 | 最终产物及路径 |
| 验收标准 | 每条都能用可观察证据判定 |
| 起始材料 | 已有文件、数据、上下文 |
| 变更范围 | 允许修改的目录与文件 |
| 执行上限 | 最大轮次、时间或费用 |

同时根据验收标准写出收尾清单，并记录当前基线（现有行为、测试结果或指标），后续改进都与它比较。

## 2. 拆图

- 一个节点 = 一个输入、一个产物、一个检查。按「节点需要读什么」划分，而不是按文件夹。
- 节点 B 使用节点 A 的产物时才连边；无边相连的节点可以并行。
- 有唯一正确答案的步骤标为**代码节点**，用脚本完成，不派给子代理。
- 在保持结果可比的前提下，节点越少越好。

把节点、边、每个节点的检查和代码节点清单写进 `graph.md`，**用户确认后再执行**。

## 3. 执行循环

1. 从 `graph.md` 选出输入已就绪的节点；相互独立的并行启动。
2. 每个节点交给独立子代理，只给它的规格、输入和检查标准。子代理只构建自己的产物，对已保存的文件运行检查，返回产物路径、结论和证据。
3. 产物经过门控（见下节）才能被下游节点使用。
4. 只退回失败的节点，从不退回整批。
5. 集成已接受的产物，运行完整检查。
6. 循环直到收尾清单全部通过、被阻塞，或达到执行上限。

节点规格写成可复用的形式，换一组输入也能直接运行。

## 4. 门控

有风险的边上设门，证据足够才放行。证据优先级：确定性检查 > 节点报告 > 模型判断。

`checks.md` 每行一个要求：

```
节点 | 要求 | 结论 | 证据
```

结论只取「通过 / 失败 / 未解决」；证据写路径或检查的实际输出，缺失的证据也要写明缺失。

- **纠正**：门控失败时，把原因、证据和「只修复此节点」的范围退回原节点；同一节点最多重试 3 次，仍失败则标为阻塞并上报。
- **沉淀**：结果被接受后，把确认有效的规则写进 `graph.md`，供下次复用。只有对所有任务都成立的规则，才向用户提议写入 `AGENTS.md`。

## 5. 交接

每个阶段结束后更新 `progress.md`：

- **图状态**：已完成、进行中、被阻塞的节点
- **产物**：已保存文件的精确路径
- **决策**：`graph.md` 改了什么、为什么
- **待办**：失败项、疑问、阻塞点
- **下一步**：下一个就绪的节点

## 6. 收尾

收尾清单每项都要有可观察证据：

- 每个节点的产物存在且可打开；
- 每个门控都在已保存的版本上通过；
- 失败项已修复或已明确声明。

因上限或阻塞中断时，返回部分状态和精确的待办步骤。最终交付：产物、`graph.md`、`checks.md`、`progress.md`，并说明检查了什么、发生了什么、还剩什么。
